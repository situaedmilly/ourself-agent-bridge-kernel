# OURHARDWARESELF Doctrine v0.1

Status: CANONICAL DESIGN / IMPLEMENTATION IN PROGRESS
Authority: OURSELF Genesis Authority
Scope: Physical, virtual, operating-system, access-surface, and ecosystem hardware realities.

## Foundational law

**NO HARDWARESELF ENTERS OURSELFECOSYSTEM BY NAME ALONE. EVERY HARDWARESELF MUST ESTABLISH IDENTITY, JURISDICTION, AUTHORITY, MOAT, AND PROOF BEFORE IT CAN BE ADMITTED AS AN OPERATIONAL REALITY.**

Hardware sovereignty is the prevention of silent authority transfer between realities. Network reachability, shared credentials, agent cognition, host privilege, or a named relationship never establish jurisdiction by themselves.

## Entity ontology

The registry MUST distinguish:

1. PHYSICAL_SUBSTRATE: independently existing physical hardware.
2. OPERATING_SYSTEM: an OS instance executing on a substrate.
3. VIRTUAL_SUBSTRATE: an emulated or virtual guest with a host boundary.
4. ACCESS_SURFACE: a transport or management interface into another reality.
5. ECOSYSTEM_REALITY: a canonical OURSELF identity or functional reality.

These types are not interchangeable and MUST NOT be counted as equivalent physical devices. A hostname is not hardware identity. An OS is not a physical substrate. An access path is not the machine it reaches. An ecosystem identity is not automatically bound to a device.

## Universal invariants

- Device identity != hostname.
- OS identity != device identity.
- Boot observed != boot trusted.
- Reachability != authorization.
- Connectivity != jurisdiction.
- Proposal != execution.
- Model != authority.
- Storage != ownership.
- Network access != trust.
- Reported capacity != measured performance.
- Observation != provenance.
- Claimed effect != verified effect.
- Valid change != authorized change.
- Recovery capability != recovery proof.

## Authority separation

COGNITION != AUTHORITY != ADMISSION != ACTUATION != EFFECT.

A model may propose. It may not self-authorize. An access surface may transport a request. It may not enlarge the caller's jurisdiction. A host may administer a guest only through an explicit, bounded host-to-guest authority contract.

## Admission lifecycle

DECLARED -> DISCOVERED -> IDENTITY_VERIFIED -> BOUND -> MOATED -> OPERATIONAL -> PROVEN.

This is a set of distinct states, not an automatic promotion pipeline. Every transition requires an explicit decision and supporting evidence. The compiler may assess prerequisites; it cannot manufacture identity, authority, attestation, or proof.

## Evidence and receipts

Every observation records its source, observer, timestamp, method, scope, limitations, and integrity digest. An unsigned observation is evidence of what an observer reported, not hardware-backed attestation. A receipt is independently verifiable only when its signature, signer identity, canonical payload, freshness, and verification chain are validated.

## Platform boundary

Implement controls according to actual platform capabilities. Preserve Apple's native boot and security model on macOS. Use supported Linux mechanisms on SELFPI. Never claim TPM, Secure Enclave attestation, secure boot, BMC, UPS, or hardware-backed key custody without direct evidence.

## Mutation law

Inventory and compiler operations are read-only. Mutation of boot policy, firmware, keys, network policy, OS configuration, or services requires a separate scoped authorization, preflight, rollback plan, and witnessed postcondition.

## Current admission posture

The November 2, 2026 Mac and Pi substrate observations are READ_ONLY and OBSERVED_NOT_ATTESTED. They do not establish IDENTITY_VERIFIED, BOUND, MOATED, OPERATIONAL, or PROVEN status for the new canonical registry.
